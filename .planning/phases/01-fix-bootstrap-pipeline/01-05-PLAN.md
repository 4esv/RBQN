<objective>
Implement REPL variable persistence and create the Phase 1 verification test suite.

Currently, each REPL line is a fresh `exec_string` call with no accumulated state. Variables defined on one line (`a←5`) are unavailable on the next (`a+1` → "Undefined identifier"). This plan adds a ReplState that accumulates variable names, values, and depths across lines, passing them to the compiler and VM via scope extension.

Purpose: REPL is a core Phase 1 deliverable (PIPE-07). The verification test suite (planned in 01-03 but never created) proves the entire phase works end-to-end.
Output: Working REPL with variable persistence. Phase 1 verification tests.
</objective>

  <action>
Implement CBQN-compatible REPL variable persistence. The approach:

**1. Create ReplState struct in repl.rs:**
```rust
struct ReplState {
    var_names: Vec<String>,    // accumulated variable names across all lines
    var_values: Vec<B>,        // current values for those variables
}
```

**2. Modify exec_string to accept REPL scope state:**
Add an optional parameter or create a separate `exec_repl_line` function that accepts:
- `var_names: &[String]` — accumulated variable names from prior REPL lines
- `var_values: &[B]` — current values for those variables

These are passed to the compiler as `comp_args[2]` (varNames) and used to build the scope in `compile_all`.

**3. The compiler integration:**
The BQN compiler accepts `⟨runtime, •BQN_SYS, varNames, varDepths⟩`. Currently `var_names` is always `empty_harr()` and `var_depths` is always `[]`. For REPL:
- `varNames` = character array of accumulated variable names (each name is a string)
- `varDepths` = array of 0s (all at depth 0)

The compiler returns variables at depth 0, positions beyond `var_am`. The compile_all function's `sc` parameter allows the compiler to emit EXTO/EXTM opcodes for these extended variables.

**4. After execution, extract new variables:**
After a REPL line executes, the returned scope may have new variables. The compiler output tells us how many new variables were created. Update `ReplState` with any new variable names and their final values from the scope.

**5. Wire into eval_line:**
```rust
fn eval_line(rt: &Runtime, line: &str, silent: bool, state: &mut ReplState) {
    match exec_repl_line(rt, line, &state.var_names, &state.var_values) {
        Ok((result, new_names, new_values)) => {
            state.var_names = new_names;
            state.var_values = new_values;
            if !silent { println!("{}", format_result(rt, &result)); }
        }
        Err(e) => eprintln!("Error: {e}"),
    }
}
```

**CBQN reference:** Look at how CBQN's `repl.bqn` or `src/main.c` handles REPL state. The key is: the compiler's varNames parameter lists all known variables, and the VM's scope extends to include them. After execution, the scope's variable slots contain the updated values.

**Important:** The `compile_all` function already has an `sc: Option<&Scope>` parameter. For REPL, create a Scope pre-populated with the accumulated variable values and pass it as `Some(&repl_scope)`. The compiler's bytecode rewriting will then emit EXTO/EXTM for references to these accumulated variables.
