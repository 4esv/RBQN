  <action>
    Implement CBQN-compatible REPL scope extension so variables persist across lines.

    CBQN's REPL approach:
    1. The compiler accepts `varNames` and `varDepths` as part of its argument array
    2. First REPL line: varNames=⟨⟩, varDepths=⟨⟩ (no existing variables)
    3. The compiler returns the bytecode plus information about new variables defined
    4. After execution, the REPL captures the scope's variable values
    5. Next REPL line: pass the accumulated varNames and varDepths
    6. The compiler's ScopeExt mechanism makes prior variables accessible

    Implementation steps:

    Step 1: In repl.rs, maintain a REPL state struct:
    ```rust
    struct ReplState {
        var_names: Vec<String>,   // accumulated variable names
        var_values: Vec<B>,       // their current values
    }
    ```

    Step 2: Modify exec_string (or create exec_repl_line) to accept and return variable state:
    - Input: code string + existing var_names + var_values
    - Build compiler args with var_names as a string array and var_depths as all zeros
    - After compile_all, the Block's root body will have `var_am` that includes both
      new variables and extension slots for existing ones
    - Create the root scope with extension data from var_values
    - Execute the block
    - After execution, extract the scope's variable values (including any newly defined ones)
    - Return the result + updated var_names + var_values

    Step 3: The compiler.rs ScopeExt mechanism needs to work. Check if it's already implemented
    or if the TODO at compiler.rs line 193 is still a placeholder. If it's a placeholder:
    - When varNames is non-empty, the compiler emits EXTO/EXTM/EXTU opcodes instead of
      VARO/VARM/VARU for variables that come from the extension
    - The VM's EXTO/EXTM/EXTU handlers access the scope extension
    - The scope extension (ScopeExt) stores the prior variable values

    Step 4: The simplest approach that avoids modifying the compiler: re-submit all prior
    definitions as a preamble. Each REPL line is compiled as:
    ```
    prior_var1←val1 ⋄ prior_var2←val2 ⋄ user_input
    ```
    This is not elegant but works without modifying the compiler's variable resolution.

    Try Step 3 first (proper scope extension). If the compiler doesn't support it yet,
    fall back to Step 4 (preamble injection).

    Step 5: Update eval_line in repl.rs to pass REPL state through.

    Step 6: Also handle the case where a REPL line defines a function: `f←{𝕩+1}`.
    The function must be serializable as a B value in the REPL state so it can be
    called on subsequent lines. Since B is Copy, storing it in var_values should work
    as long as the underlying Derived objects are not garbage collected (they aren't —
    no GC exists).
