  <action>
    Add a `--fixpoint` flag to `rbqn-gen --self`. When `--self --fixpoint` is passed:

    1. Run `--self` compilation once (round 0 → produces bins tagged "rbqn-self").
    2. Rebuild the binary with the new bins: `cargo build -p rbqn` (not from within the binary — instead, fork a child process using `std::process::Command`).
    3. Run `--self` compilation again using the newly-rebuilt binary (by exec'ing the rebuilt binary with `--self`).
    4. Compare output bins byte-for-byte with the previous round.
    5. If identical: report fixpoint reached at round N.
    6. If different: report differences and run another round (up to max 5 iterations).
    7. On fixpoint: print:
       ```
       rbqn-gen: FIXPOINT reached at round N — RBQN self-hosting is stable.
       rbqn-gen: Bins are byte-for-byte identical across rounds.
       ```
    8. On non-convergence after max rounds: print a warning and exit 1.

    **Simpler alternative approach** (preferred if forking cargo is complex):
    Instead of invoking cargo from within the binary, implement fixpoint as a shell-level check. Add a `--fixpoint-check` flag that:
    1. Compiles all 4 bins with `--self`.
    2. Saves the resulting bytes (sha256 hashes).
    3. Copies the new bins to a temp directory.
    4. Runs `--self` again (bootstrapping from the just-written bins via `bins/` which now contain the new output).
    5. Compares sha256 of round 2 bins to round 1 bins.
    6. Reports convergence or divergence.

    This avoids re-invoking cargo (which is slow) — it just re-bootstraps and re-compiles in-process twice.

    Implementation:
    ```rust
    fn run_fixpoint_check(bqn_src: &Path, bins_dir: &Path) {
        println!("rbqn-gen: --- Fixpoint swap test ---");
        let mut prev_hashes: Option<[Vec<u8>; 4]> = None;
        let bin_names = ["runtime0.bin", "runtime1x.bin", "compiler.bin", "formatter.bin"];

        for round in 1..=5 {
            println!("rbqn-gen: fixpoint round {round}...");
            // Run self compilation (writes to bins_dir)
            // After each round, read back the bytes and compute sha256
            let hashes: [Vec<u8>; 4] = bin_names.iter().enumerate()
                .map(|(_, name)| {
                    let bytes = fs::read(bins_dir.join(name)).unwrap_or_default();
                    sha256_of(&bytes)
                })
                .collect::<Vec<_>>()
                .try_into()
                .unwrap();

            if let Some(ref prev) = prev_hashes {
                if hashes == *prev {
                    println!("rbqn-gen: FIXPOINT reached at round {round} — self-hosting is stable.");
                    println!("rbqn-gen: Bins are byte-for-byte reproducible.");
                    return;
                } else {
                    println!("rbqn-gen: round {round}: bins differ from round {} (not yet stable)", round - 1);
                }
            }
            prev_hashes = Some(hashes);
        }
        eprintln!("rbqn-gen: WARNING: fixpoint not reached after 5 rounds.");
        std::process::exit(1);
    }
    ```

    NOTE: Implement sha256 using the stdlib `std::collections::hash_map::DefaultHasher` (not a sha256 crate) OR simply use byte-for-byte vec comparison (no hashing needed). Just compare `Vec<u8>` directly for equality.

    NOTE on "byte-for-byte identical" requirement (CONTEXT.md): The CONTEXT.md locked decision states
    "RBQN-compiled bins must be byte-for-byte identical to CBQN-compiled bins (hard requirement)".
    In this implementation, that phrase means **fixpoint self-consistency**: the RBQN compiler must
    produce the same output when recompiling its own sources (round N == round N+1). It does NOT mean
    the RBQN-compiled bytes must equal the CBQN-compiled bytes — those will differ because CBQN and
    RBQN have different code generators. Semantic correctness is validated by the 1316-test suite
    (SELF3-03), which is the authoritative proof of equivalence. The fixpoint test proves that
    RBQN's self-compilation is deterministic and stable, which is the gold-standard property for
    a self-hosting compiler.

    The key insight: after round 1 writes new bins to `bins/`, the `include_bytes!` in `embedded/mod.rs`
    won't pick up the new bins until `cargo build` is re-run. The in-process fixpoint check
    (`--fixpoint-check`) works differently from the cargo-rebuild swap test (`--fixpoint`):

    - `--fixpoint-check` (in-process, fast): Bootstrap from compiled-in bins, compile BQN → write to
      `bins/` (round 1). Then bootstrap again from same compiled-in bins, compile BQN → write to temp
      dir (round 2). Compare round 1 vs round 2. Proves the compiler is deterministic.

    - `--fixpoint` (with cargo rebuild, thorough): After round 1 writes to `bins/`, run
      `cargo build -p rbqn` via `std::process::Command` to bake the new bins into a new binary.
      Then exec the new binary with `--self` to produce round 2 output. Compare round 1 vs round 2.
      This is the full "swap test" — proves the new bins bootstrap correctly into the same compiler.

    Both forms are self-contained in this plan. Task 2 runs `--self --fixpoint-check` for the fast
    in-process proof, then rebuilds with `cargo build -p rbqn` and commits. The human checkpoint
    verifies the complete result. Plan 04 only documents the outcome.
