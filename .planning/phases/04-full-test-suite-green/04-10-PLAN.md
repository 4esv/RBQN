Implement •HashMap as a constructor function:

**Registration:**
- Add `"hashmap" => m_sys_fn(170)` in sys_name_to_b.
- In sysfn.rs, dispatch_sys_c1 case 170 creates a HashMap.

**Constructor semantics:**
- `•HashMap ⟨⟩` or `•HashMap 0` creates an empty HashMap.
- `•HashMap ⟨keys, values⟩` creates a HashMap initialized with the given key-value pairs.
- Returns a namespace-like object with methods: `Get`, `Has`, `Set`, `Delete`, `Keys`, `Values`, `Count`.

**Implementation approach:**
Use a Rust `HashMap<u64, (B, B)>` where the u64 key is computed via `•Hash` (the existing hash function). Store the HashMap in a new global store (similar to DERIVED_STORE), or embed it within a namespace.

Simpler approach: create a namespace with sys_fn fields that carry the HashMap reference:
1. Create a `static HASHMAP_STORE: LazyLock<Mutex<HashMap<u64, HMap>>>` where HMap = `HashMap<u64, (B, B)>` (hash → (key, value)).
2. Each •HashMap instance gets a unique ID.
3. The namespace fields (Get, Has, etc.) are sys_fn values that carry the HashMap ID in a closure (or use a convention where the namespace scope slot 0 holds the ID).

For MVP, implement:
- `Count`: returns number of entries (monadic)
- `Keys`: returns array of keys (monadic)
- `Has`: `key Has hm` returns 0 or 1 (dyadic — note CBQN convention: `hm.Has key`, so monadic c1)
- `Get`: `key Get hm` returns value (dyadic — same: `hm.Get key`, monadic c1 with bound self)
- `Set`: `⟨key, value⟩ Set hm` or `hm.Set ⟨key, value⟩` — mutates in place

If the full implementation is too complex, a minimal version that supports `•HashMap ⟨⟩` returning a namespace with stub methods is acceptable — the official test suite does not test •HashMap.
