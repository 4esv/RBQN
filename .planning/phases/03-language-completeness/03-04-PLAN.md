Two targeted fixes in derive.rs:

1. Add case 203 to `dispatch_sys_c2` (around line 1188, before the `_` catch-all). Dyadic √⁼ means `w√⁼x = x⋆w` (raise x to the power w). Implementation:
```rust
203 => { // w √⁼ x = x⋆w (dyadic sqrt-inverse = power)
    let x_f = x.o2f();
    let w_f = w.o2f();
    B::m_f64(x_f.powf(w_f))
}
```
This must handle arrays too — if x is an array, iterate with pervasive pattern. Check if `rbqn_prim::arith_dyad` has a power function already (`pow_c2` or similar) and use that instead of bare `.powf()` if available. If no array-capable dyadic power exists, implement inline: extract both as f64 scalars and compute x.powf(w).

2. Fix dyadic +⁼ for character arithmetic. The current `native_inverse_reg(0)` returns `m_native_fn(5)` (√) which is correct for monadic `+⁼x = √x`. But dyadic `w+⁼x` should NOT use √ — it should fall through to the BQN runtime inverse for character subtract behavior (`3+⁼'d' = 'a'`). In `dispatch_sys_c2` case 10 (nativeInvReg dyadic), if the function being inverted is `+` (prim 0), do NOT call c2 on the monadic inverse (√) — instead fall through to the runtime inverse. The simplest fix: in `inv_reg`, return None for dyadic inverse of `+` so the runtime handles it. Alternatively, add a `inv_reg_c2` path that distinguishes monadic vs dyadic cases.

Look at how case 10 currently works: `let inv_fn = inv_reg(w); c2(inv_fn, w, x)`. The problem is `inv_reg(+)` returns `√`, and `c2(√, 3, 'd')` doesn't do character subtraction. The fix: for prim 0 (+), the dyadic inverse should be `-` (subtract), not √. Create a separate `inv_reg_dyadic(prim_idx)` function or add a dyadic-specific table. For `+`, dyadic inverse is `-` (prim 1). For other prims, dyadic inverse typically matches the monadic one or falls through to runtime.

<task type="auto">

Two improvements to `try_structural_under` in modifiers.rs:

1. **Functional-k Under**: Currently the `F⌾(k⊸↑)` pattern in try_structural_under (line ~706) extracts `left_op` as a literal value. But when k is a function (e.g., `(2÷˜≠)⊸↑`), left_op is a function, not a number. Detect this: if `left_op.is_fun()`, evaluate `k` on `x` first: `let k_val = c1(left_op, x);` then use `k_val` in place of `left_op` for the take/drop operations. This handles `F⌾((2÷˜≠)⊸↑)` which computes k = half of array length.

Specifically, in the k⊸↑ arm (NativeFn prim_idx: 26), before calling `c2(take_fn, left_op, x)`:
```rust
let k = if left_op.is_fun() || left_op.is_md1() || left_op.is_md2() {
    // k is a function — evaluate on x to get numeric value
    c1(left_op, x)
} else {
    left_op
};
```
Then use `k` instead of `left_op` for the take/drop calls. Apply the same pattern to the k⊸↓ arm (prim_idx: 27).

BUT: there's a subtlety. When left_op is a function like `(2÷˜≠)`, the ⊸ (Before) modifier makes this into `{(2÷˜≠)𝕩}⊸↑` meaning the left operand of ⊸ IS already a derived function. The issue is: left_op in the current code is `gd.f` which is the left operand of the ⊸ modifier. If it's a derived function (fork, atop, etc.), it needs to be called as c1(left_op, x) to get the numeric k. Check if left_op is already a number (is_f64) — if so, use directly. If it's a function/derived, evaluate it on x.

2. **Computational Under fallback**: For patterns that aren't structurally handled (like `⊏⎉1`), don't just return None — fall through to the BQN runtime's Under implementation if available. Check if there's a `RT_UNDER` or equivalent runtime function. If `try_structural_under` returns None and a runtime Under function exists, call it. This is likely already handled in the caller (`under_c1`) — verify and confirm the fallback path works. If under_c1 already falls through to runtime Under on None, no code change needed; just document that the ⊏⎉1 patterns are handled by runtime.
