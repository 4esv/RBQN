<task type="auto">
  <name>Task 1: Debug and fix string literal compilation ("Double subjects" error)</name>
  <files>crates/rbqn-vm/src/vm.rs, crates/rbqn-vm/src/compiler.rs, crates/rbqn/src/main.rs</files>
  <action>
The BQN compiler (running in our VM) compiles `"hello"` into bytecode. When this bytecode executes, it triggers "Assertion error: [1, 0]: Double subjects (missing ‿?)". This is a runtime assertion from the BQN runtime, meaning the compiled bytecode is structurally wrong — the VM is producing a stack state where two subjects appear consecutively without an operator between them.

**Debugging approach (use RBQN_COMP_TRACE=1):**
1. Run `RBQN_COMP_TRACE=1 CBQN_PATH=/path/to/CBQN cargo run -p rbqn -- -p '"hello"'` to see the bytecode the compiler generates for string literals.
2. Compare with CBQN: run `CBQN_PATH=/path/to/CBQN cbqn -e '•Show •internal.Comp "\"hello\""'` (or similar) to see what CBQN's compiler produces for the same input. The bytecode and object arrays should match.
3. The "Double subjects" error means two values were pushed to the stack without a consuming operation. Check: Does the PUSH opcode for the string object resolve correctly? Is the string stored as a single character array in `objs`, or is it being split?
4. Check the PUSH→ADDI/ADDU transformation in compiler.rs: when the compiler produces `PUSH idx` for a string constant, `comp.objs[idx]` should be a character array (tagged ARR). The `is_val()` check determines ADDI vs ADDU — a string array should be `is_val() == true` (tag FFF7 = ARR), producing ADDI.
5. In the VM execution loop (vm.rs `eval_bc`), verify ADDI correctly pushes the object as an immediate value without further processing.

**Likely root causes to investigate:**
- The compiler's PUSH opcode may be double-pushing (once for the PUSH and once for something else)
- The string may be getting decomposed into individual characters by the LSTO/ARMO opcodes
- The object index in PUSH may be wrong, pulling the wrong object from comp.objs
- The bytecode rewriting in compile_block may be mishandling PUSH offsets

**Fix:** Once root cause is identified, apply the minimal fix to compiler.rs or vm.rs. Do NOT change the BQN compiler itself (it runs as bytecode in our VM) — the bug is in how our VM executes that bytecode or how compile_block translates it.

After fixing, verify: `rbqn -p '"hello"'` should output `"hello"`. Also verify `rbqn -p '•Out "hello"'` prints `hello` to stdout.
  </action>

<task type="auto">
  <name>Task 2: Fix dyadic arithmetic and modifier resolution through compiler pipeline</name>
  <files>crates/rbqn-vm/src/vm.rs, crates/rbqn-vm/src/compiler.rs, crates/rbqn-vm/src/derive.rs</files>
  <action>
Two related symptoms: `3×4` returns `3` (left argument returned instead of product), and `+´1‿2‿3` fails with "Interpreting non-1-modifier as 1-modifier".

**Root cause hypothesis:** The BQN compiler resolves primitives by index into the runtime array. When the compiler bytecode does `PUSH rt_idx` to load `×` or `´`, the index maps to the wrong position in the runtime array. This would happen if:
- The runtime array passed to the compiler (`comp_args[0]`) has elements in a different order than the compiler expects
- OR the compiler's PUSH indices are being shifted by the bytecode rewriting in compile_block
- OR the FN2C/MD1C opcodes are dispatching on the wrong operand

**Debugging approach:**
1. Run `RBQN_COMP_TRACE=1 CBQN_PATH=/path/to/CBQN cargo run -p rbqn -- -p '3×4'` and examine:
   - The `objs` array: which index is `×`? What is at that index?
   - The bytecode: is `FN2C` being generated? Does it consume the right operands?
2. Compare with `1+1` (which works): what's different in the bytecode structure?
3. For `+´`: Check what object the compiler places for `´`. It should be a 1-modifier (MD1). If the runtime array has `´` at a different index than what the compiler expects, the PUSH will load something that's not a modifier.
4. Check `exec_string_inner` in main.rs: the `rt_arr` passed to the compiler must be the same 64-element runtime array that the compiler was compiled against. Verify the elements are in the expected order (runtime[0] = ⌊, runtime[1] = ⌈, etc. per CBQN's r1Co convention).

**Likely root causes:**
- The runtime array may have wrong element ordering (bypass produces natives in fruntime order, but the compiler expects r1Co order after runtime1 processing)
- compile_block's PUSH→ADDI/ADDU may corrupt the object reference when using u64 encoding (the low/high i32 split)
- The FN2C opcode may be popping arguments in wrong order

**Fix:** Once root cause is identified, fix the specific indexing or dispatch issue. This likely involves either:
- Fixing the runtime array order passed in `comp_args`
- Fixing the PUSH encoding in compile_block
- Fixing operand order in eval_bc for FN2C/MD1C

After fixing, verify both symptoms are resolved.
  </action>
