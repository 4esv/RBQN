**Architecture note from RESEARCH.md:** The BQN evaluator calls `c2(f, w, x)` one call at a time with no forward lookahead. True lazy fusion across arbitrary expression trees is not feasible in Phase 5. Instead, implement an **explicit fused dispatch API** that the executor can call when it detects a pattern of consecutive elementwise ops.

**Approach: Thread-local fusion accumulator.**

The key insight: when `pervasive_dyad` runs for `a+b` on a large array and produces an intermediate result, and then `2×(a+b)` immediately calls `pervasive_dyad` again with that intermediate as input, we can detect this and fuse.

Implementation:

1. **In `gpu_runtime.rs`, add a thread-local pending GPU buffer mechanism:**
```rust
use std::cell::RefCell;

struct PendingGpuResult {
    buf: GpuBuffer,       // result still on GPU
    arr_id: u64,          // the BqnArr ID that was created as placeholder
    shape: Vec<usize>,
    fill: Option<B>,
}

thread_local! {
    static PENDING_GPU: RefCell<Option<PendingGpuResult>> = RefCell::new(None);
}
```

2. **Modify `gpu_arith_binary`** to check if either input is a pending GPU buffer (by matching arr_id). If so, skip the re-upload and use the existing GPU buffer directly, accumulating ops via FusionBuilder:

```rust
pub fn gpu_arith_binary(op: &str, w_arr: &BqnArr, x_arr: &BqnArr) -> Option<BqnArr> {
    let gpu = get()?;
    let len = w_arr.ia();
    if !should_dispatch("arith", len) { return None; }

    // Check if either operand is a pending GPU result
    let pending = PENDING_GPU.with(|p| p.borrow_mut().take());

    if let Some(pending) = pending {
        // One operand is already on GPU — fuse
        let (gpu_buf, other_arr) = if w_arr has matching ID {
            (pending.buf, x_arr)
        } else if x_arr has matching ID {
            (pending.buf, w_arr)
        } else {
            // Neither matches — flush pending, proceed normally
            // ... download pending, continue
        };
        // Upload the other array, run fused op, store new pending
    }

    // Normal path: upload both, compute, store result as pending instead of downloading
}
```

**Simpler approach (recommended for Phase 5):** Instead of the complex pending-buffer tracking, expose `gpu_fused_arith` as a standalone function that takes a list of `(op, scalar_or_array)` operations and builds a FusionBuilder:

```rust
pub fn gpu_fused_arith(
    ops: &[(&str, Option<f64>)],  // (op_name, optional_scalar)
    a: &BqnArr,
    b: Option<&BqnArr>,
) -> Option<BqnArr>
```

This function:
1. Checks GPU availability and threshold on `a`
2. Creates a `FusionBuilder`, pushes ops mapped to `FusedOp` variants
3. Uploads input array(s)
4. Creates output buffer
5. Calls `builder.execute()`
6. Downloads and returns result

**In `arith_dyad.rs`, add a fused dispatch hook:**
```rust
type GpuFusedFn = fn(ops: &[(&str, Option<f64>)], a: &BqnArr, b: Option<&BqnArr>) -> Option<BqnArr>;
static GPU_FUSED_HOOK: OnceLock<GpuFusedFn> = OnceLock::new();
pub fn register_gpu_fused(f: GpuFusedFn) { let _ = GPU_FUSED_HOOK.set(f); }
```

And expose a public API for explicit fused calls:
```rust
pub fn try_fused_arith(
    ops: &[(&str, Option<f64>)],
    a: &BqnArr,
    b: Option<&BqnArr>,
) -> Option<BqnArr> {
    GPU_FUSED_HOOK.get().and_then(|f| f(ops, a, b))
}
```

This allows future VM-level optimizations to detect fuseable patterns and call `try_fused_arith` directly. For Phase 5, the FusionBuilder wiring is the deliverable — true expression-level fusion detection is documented as future work.
